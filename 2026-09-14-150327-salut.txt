● Am rezultatele explorării. Iată tabloul actual și cum văd că s-ar potrivi
  ideea ta:

  Ce există acum
  - Nu există log-uri pe fișier propriu-zise (nici CW decoder, nici PSK
    Reporter) — jurnalul de QSO e în SQLite (QsoDbHelper).
  - Ce chiar există ca fișiere sunt exporturile: ADIF (AdifExporter.java) și
    backup complet criptat (BackupHelper.java + BackupCryptoHelper.java), scrise
    fie în Downloads/YaesuCatControlADV/ (API ≥29, via MediaStore), fie legacy
    pe API <29.
  - Există deja share prin FileProvider + Intent.ACTION_SEND (butonul de share
    ADIF din EcranSetariProprii.java).
  - Nu există niciun server HTTP embedded — zero NanoHTTPD/Ktor/ServerSocket.
    Toată rețeaua e HttpURLConnection/Socket brut.
  - minSdk 26 / targetSdk 35, INTERNET + ACCESS_NETWORK_STATE deja declarate,
    usesCleartextTraffic="true" deja pornit — deci un server HTTP local n-ar
    cere permisiuni noi majore (poate doar ACCESS_WIFI_STATE ca să afișezi IP-ul
    telefonului în UI).

  Ce ai de ales, practic

  1. Domeniul expus: doar backup-urile JSON + ADIF-urile exportate (simplu,
     puține fișiere, risc mic) vs. un file-browser generic peste tot cache/files
     dir (mai flexibil, dar expune mai mult decât ai vrea, inclusiv eventual
     chei/token-uri dacă nu ai grijă cu ce salvezi acolo).
  2. Librărie:
     - NanoHTTPD (~tiny, o singură clasă, foarte folosit pe Android pentru exact
       acest caz) — cel mai simplu de integrat.
     - Server minimal pe HttpServer din com.sun.net.httpserver — nu e garantat
       pe toate ROM-urile Android, nu recomand.
     - Ktor embedded server — mai greu, motivat doar dacă vrei și alte
       rute/API-uri mai complexe.

     Dat fiind că proiectul deja nu are nicio dependență de networking modernă,
     aș merge pe NanoHTTPD: o singură dependență mică, un singur fișier de cod,
     ușor de revizuit pentru securitate.
  3. Ciclul de viață: pornit ca Service (poate chiar ForegroundService, aveți
     deja ClusterService ca precedent) doar cât ești pe un ecran de
     setări/backup, sau permanent cât rulează aplicația? Aș recomanda on-demand,
     pornit manual dintr-un buton "Enable file server" din EcranSetariProprii,
     cu auto-stop după un timeout sau la ieșirea din ecran — nu vrei un port
     deschis permanent fără să știi.
  4. Securitate minimă: fără autentificare cineva din aceeași rețea WiFi ar
     putea downloada backup-ul (care conține parole cluster etc., deja criptat,
     dar tot nu ai vrea acces liber). Opțiuni: un PIN/token afișat pe ecran care
     trebuie pus în URL, sau pur și simplu documentezi riscul și te bazezi pe
     faptul că e rețea locală/personală. Ce prag de risc accepți aici?

  Ce zici, mergem pe NanoHTTPD + server pornit manual, limitat la folderul de
  backup/export (nu file-browser generic), cu un token simplu în URL pentru
  minim de protecție?
